# 语义删减判断规则

这份规则给 Agent 写 `semantic_plan.json` 时用，是操作清单，不是新的剪辑算法。字段格式、校验规则、置信度限制一律以 `video-editor/SKILL.md` 为准。思路参考了本机 `~/.agents/skills/oil-studio/references/editing-judgment.md`，本文件自带，不依赖那份文件存在。

## 前提

先从头到尾读完全部 `semantic_context.json` 的窗口和 `atoms`，弄清楚这条视频在讲什么、分几段，再开始标删减。长片会切成多个滑窗，窗口之间有重叠部分，不要只看第一个窗口就下结论。语义判断只依据转录文字和时间戳，不重新听猜，也不把「这里有停顿」直接等同于「这句是废话」。停顿压缩是 `video-editor` 在步骤 3 做的事，Agent 这一步只处理文字层面的口误、重讲和废案。

## 重说簇整段扫描（长片必做）

逐句挑废句会漏掉最该删的部分。口播里常见一种结构：讲者连续两三次用同一个词起头，每次都说到一半停下，直到某一句才把主谓宾说完整，后面接着展开举例。单看其中任何一句都只像「有点啰嗦」，只有把整簇连起来读，才能判断哪一句是落地句、前面整片都是废案。这正是 `calling-agent` 相对规则匹配的价值，Agent 必须真的通读全文再下结论。

识别时按顺序通读 `atoms`，遇到下面几个特征同时出现就先标成候选簇，不要急着一条条写删减：相邻 atom 反复出现同一组起头词（`以前呢`、`但是呢`、`也看过`、`这个项目`、`这个软件呢就`、`他是解决`）且都断在半句或只有主语；簇内某句自己就带一遍重复；簇之后有一句主谓宾完整，且后文继续展开或举例。

Clothespeg 743s 长片的开场是标准样本。U0005「以前吧我就是。」、U0006「以前呢我用过很多的这个剪切板的这个以前呢我用过很多剪切板的这种工具。」、U0007「以前呢。」、U0008「呃众所周知呢。」连续四次起头，U0009–U0010「众所周知，就是麦克的这个剪切板呢并不是特别的好用。」才成句；U0012「以前呢我也用过很多呃捷线版的这种工具，」接 U0014–U0018 展开付费、免费、试用、买过，才是「用过很多工具」这条信息的落地表述。C 档逐句挑废句只删了 U0005 和 U0008，U0006、U0007 留在成片里，听起来仍是「前面好几段都是废的」。

处理时把整簇写成**一条**删减：`remove_start_id` 到 `remove_end_id` 覆盖全部废案 atom，`cut_until_id` 指向下一个 atom，`replacement_ids` 指向落地句，`reason` 写明删后前后句怎么接上，`category` 用 `abandoned_take`，`confidence` 用 `high`。

有三条硬检查。第一，簇内 atom 有没有被已有删减当成 `replacement_ids`；有就必须改写那条旧删减，把替代句改指簇后的落地句，否则校验器会把旧删减整条丢弃，簇头反而留下变成孤立废话。D 版就踩过这一条：C 版删 U0005 时把 U0006 当作替代句，直接新增「删 U0006–U0007」会让 U0005 不再被删，正确做法是把那条改写成整簇 U0005–U0007、替代句改指 U0012。第二，`replacement_ids` 指向的落地句不能被任何删除区间覆盖，也不能只是后续句子的宾语或下一步动作。第三，删后把保留 atom 的文字按顺序拼出来读一遍，确认成句、没丢只出现一次的信息；D 版开场拼出来是「大家好，今天呢我给大家介绍一个我外部coding的一个软件。这个软件…众所周知，就是麦克的这个剪切板呢并不是特别的好用。以前呢我也用过很多呃捷线版的这种工具，有的是付费的…」，衔接成立。

边界也要清楚。删减粒度是 atom，`removed_quote` 必须逐字覆盖 `remove_start_id` 到 `remove_end_id` 的全部文字，没有「删半句」的字段。U0060「他是解决了麦克自己截屏的这个他是解决麦克自带的这个截屏的一个问题。」、U0155「你可以认为就他就你可以认为他就变成了一个土豆Li的这么一个功能。」这类同一个 atom 里说两遍的，只能整句留或整句删；含独有信息时一律留。短犹豫音不算簇，交给停顿压缩。

## 重说候选的五步核对

一条删减要能同时回答五个问题，任何一步答不清就保留，或把置信度降到 `medium` 让校验器挡掉：

1. 前一句的原话是什么，待删区间是否逐字覆盖完整。
2. 有没有明确的放弃或重来标记，例如「不对」「重新说」「等一下」，还是只是语气上的重复。
3. 后一句是否真的在重述或纠正同一条信息，而不是接着讲新内容。
4. 删掉之后前后句连起来是否仍然完整、听得懂。
5. `replacement_ids` 指向的片段是否确实保留在最终计划里，有没有被同一批删减覆盖。

## 必留

- 只出现一次的信息：数字、版本、名称、步骤、条件、提醒、警告、结论、结果。
- 转折处前后两半。转折词后面的内容常常是新信息，不要因为前半句像废案就连带删掉。
- 演示动作的口头说明。屏幕上正在发生什么，往往只在这句话里交代过一次。
- 没有明确替代话术的片段。宁可漏删，不要误删。

## 逐项复核 fillerCandidates

候选列表里的「嗯」「呃」「这个」「那」等要一条条看，不能整批标删。短于 4 个字的犹豫音主要由停顿压缩处理，通常不需要写进 `semantic_plan.json`。真正要写进计划的是成句的废案，例如说了一半放弃的开场、重复一遍的完整句子、说错的术语后立刻改正。

## 类别

按 `video-editor` 的取值填写，用于报告可读性，不参与时长判断：`abandoned_take`（说停并放弃的一段）、`false_start`（开头起错）、`explicit_restart`（明确重来）、`slip`（口误后改正）、`filler`（成句的填充）、`delivery_cleanup`（局部表达清理）、`recording_meta`（录制相关的自言自语）。`delivery_cleanup` 和 `self_correction` 超过 2.5 秒会被校验器拒绝。

## 交付前自检

- `source` 字段从 `semantic_context.json` 原样复制。
- `removed_quote` 逐字覆盖 `remove_start_id` 到 `remove_end_id` 的全部原话。
- `replacement_quote` 与 `replacement_ids` 对应，且这些片段没有被别的删减覆盖。
- `confidence` 只用 `high` 或 `medium`，拿不准就不写这条。
- `reason` 写清楚「前一句为什么是废案」和「后一句为什么算重述」，不要只写「重复」。
- 写完后运行 `cut --dry-run --semantic-plan`，看 `semantic_cuts` 的采纳数与 `edits` 条数是否一致。不一致时按校验器规则改计划，不要去改 `kept_intervals`。
